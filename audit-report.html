Read-only audit of geezery/DockFlip at commit 3181f73 (version 0.5.2), 10 November 2026. About 11,800 lines of Swift in 147 source files, 5,600 lines of tests, plus build, release, site and docs. Read on Linux: nothing could be built or run.

Executive summary

DockFlip is in good health. The code follows its own house rules almost everywhere: the scans for networking, repeating timers, SwiftUI macros, titles in logs and deadlock patterns all came back clean, pure rules are split out and tested (426 tests in 79 suites), and the docs match the code to a degree that is rare. Nothing found is critical, and there is no data-loss bug.

The problems gather in three places. First, trust in the shipped binary: the app that holds Accessibility is signed without the hardened runtime, the release key's password is in the repository, and any v* tag is signed and published unchecked. Second, the thumbnail privacy boundary: private browser windows are recognised only by English words, pictures survive the off switch, and an open switcher keeps them through a screen lock, all in a 397-line class with no tests. Third, the edges of the app's life: macOS's own ⌘Tab stays off after a crash or a launch without permission, a late permission grant starts nothing, and the window order at launch is no longer seeded.

A pattern runs through most findings: the pure value types are sound, and the bugs sit in the untested AppKit glue around them. About half of all findings are under an hour each.

F01

The app that holds Accessibility is signed without the hardened runtime

HighSecurityBuild, CI & releaseEffort S · under 1 h

Evidence

.github/workflows/release.yml:67
codesign --force --timestamp=none --keychain "$KEYCHAIN" --sign "$SIGN_HASH" build/DockFlip.app
Makefile:63, Makefile:66
codesign --force --timestamp=none --keychain "$(SIGN_KEYCHAIN)" --sign "$(SIGN_ID)" "$(APP)"; \
...
codesign --force --sign - "$(APP)"; \
grep for runtime over Makefile, .github and scripts/*.sh
(no match)

Why it matters here

DockFlip holds the Accessibility grant and runs session-wide mouse and key event taps. Without --options runtime, macOS honours DYLD_INSERT_LIBRARIES for the binary, so any process running as the user can start DockFlip with an injected library and act with its grant: read window and tab titles, press buttons in other apps, see keys while a tap is on. On managed Macs the PPPC profile from docs/IT.md grants this silently.

That sits badly beside SECURITY.md, whose whole point is that DockFlip can be trusted next to every window.

Recommended fix

Add --options runtime to all three codesign calls for the app (it works with self-signed and ad-hoc identities; the app links only Apple frameworks). Add a check to CI and the release job: codesign -d --verbose=4 build/DockFlip.app 2>&1 | grep -q 'flags=.*runtime'. Test once on a Mac that thumbnails (ScreenCaptureKit) and the event taps still work under the hardened runtime.

Why it matters here

Why it matters here

Needs investigation

Plausible from reading, but only a Mac can prove or disprove them. Not counted as findings.

  • An open Dock list may close under the mouse on any refresh. WindowListPopup.presentUnmeasured hides the list when source.anchor(for:) is nil, and DockController.anchor(for:) needs hovered, which is set to nil when the Dock reports no highlighted icon (DockController.swift:162-169, 285-288; WindowListPopup.swift:139-144). If the Dock reports that when the mouse moves up onto the list, then closing a window with ×, tabs arriving or a title change closes the list. listIcon is kept for this crossing but anchor(for:) does not use it. Certain in code; whether the Dock sends that report needs a Mac.
  • Saved window numbers may be trusted across logout and login. PlacementMemory and UsageTracker drop their window lists only when the boot time changes (Core/BootTime.swift:20-22). If the window server's counter starts again at logout without a restart, old entries collide with new windows and the next display change moves unrelated windows. Compare window numbers before and after logging out.
  • Does NSWorkspace.didLaunchApplicationNotification fire for the Dock after killall Dock? DockController.swift:85-94 relies on it to attach again. If it does not fire for this kind of process, hover lists die at every Dock relaunch.
  • Firefox and Zen tabs on a fresh launch. SCOPE.md says Firefox turns on its accessibility engine when asked for its tabs; no code sets AXEnhancedUserInterface or AXManualAccessibility. Check that the tab strip answers a plain read without VoiceOver running.
  • Does macOS's switcher win over AltTab once DockFlip turns it back on? Decides how visible the finding about turning macOS's ⌘Tab back on is to people who run both apps.
  • Hardened runtime with thumbnails and the self-signed identity. Confirm on a Mac that ScreenCaptureKit captures and the event taps work after adding --options runtime.
  • AXObserverAddNotification off the main thread. AppSubscriber and WindowSubscriber call it on the app's queue for an observer whose run-loop source lives on the main run loop. AltTab does the same; thread safety is not documented.
  • Ghost windows. The window-server list with .optionAll also names windows an app closed but did not release. For apps tracked without notifications, or a window destroyed during a read, such a window could stay in ⌘Tab as "on another desktop".
  • Stage Manager. It is the largest open bug area in comparable tools, and neither the source nor the docs mention it. Test snapping, Snap Assist and ⌘Tab with it on.
  • Holding ⌘Tab probably does not repeat. A Carbon hot key fires once per press, and SwitcherInput.from returns nil for Tab with ⌘. Windows keeps cycling while Tab is held.
  • The com.apple.screenIsLocked announcement. Undocumented, and the only signal for a lock without sleep. If macOS renames it, kept pictures survive a lock. A line in the release checklist would cover it.
  • Repository settings not visible from the checkout. Whether v* tags have a ruleset, the release secret an environment, and main a required CI check.
  • land-gate.ps1 with two gates at once. Remove-Leftovers (lines 77-90) deletes any land/* branch with no listed run; a second gate could delete the first one's branch in the seconds before its run is listed.

What is in good shape

  • No waiting on other apps on the main thread. Reads, focus, move, close, probe and subscriptions go through AppQueues with per-app order and stop-after-first-timeout, and WindowRegistryTests asserts that nothing runs on main. Keep this rule exactly as it is, and bring tab reading under it.
  • The house rules hold in the code. No networking (SECURITY.md's own grep prints nothing), no repeating timers or polling, no SwiftUI macros, no DispatchQueue.main.sync, no semaphores, no try! or fatalError, and every one of about 60 public log interpolations carries an app name, a count or a code, never a title.
  • Event taps are scoped and heal themselves. The two keyboard taps are on only while the switcher is open, a tap found on while closed turns itself off, and all three taps are switched back on after a timeout. This is what makes SECURITY.md's keyboard claims true.
  • Pure rules with real tests. SnapEngine, SnapZone, SnapDrag, DockPress, DockClick, DockAim, SwitcherSelection, SwitcherRelease, CleanupEngine, CaptureQueue, PreviewFreshness and more: small value types, tests named after what the user sees, sleeps injected instead of slept. SwitcherController taking closures and a presenter is the pattern to copy for the untested coordinators.
  • Private calls are named, counted and shown. SelfCheck → UnavailableFeature → status lines in the menu → the debug log, with a CI canary for the ⌘Tab switch.
  • Localisation is enforced. 150 keys, identical in all 15 languages, every %@ and %ld matching in count and order, every key used, with a mutation-style self-check in the tests. An independent script agreed.
  • Docs match the code. Every shortcut table, the four settings, the browser and password-manager lists, and every number checked (64 and 16 pictures, 150 ms, 250 ms, 1/2/4 s, three days, 8 points) are right, and several are pinned by tests.
  • CI and release basics. contents: read on pull requests with no secrets, the tag passed through env and never pasted into a script, attestations and checksums for the disk image, the package and the profile, and a launch check that starts the real app.
  • Stored data is small and clean. Only settings, bundle ids, window numbers, dates and frames; at most 8 layouts; restore frames pruned on every write; readers reject malformed entries. No title is stored anywhere.
  • Clean Up never acts on its own. Suggest-only, polite quit, a follow-up that brings a save prompt forward, unticked rows stay unticked.

Feature ideas what would make DockFlip better

Beyond the audit, this section answers the question of what would make DockFlip better still. Every idea was held to SCOPE.md's rule (a Windows user misses it in the first week and still after a month), adds no setting, needs only Accessibility, and avoids the shortcuts already taken. Ranked by value against effort.

How far to trust it: what comparable tools' users ask for comes from issue titles and vote counts of AltTab, DockDoor and Rectangle. The Windows behaviours are from memory and should be checked on a PC before building. Nothing was tried on a Mac.

I01

⌃⌥↑ brings back what ⌃⌥↓ just minimized

Value HighEffort SFits SCOPE

Windows: Win+↓ minimizes, and Win+↑ straight after restores the same window.

In DockFlip: Today ⌃⌥↑ after a minimize maximizes whichever window is now in front: a wrong-window surprise. Remember the window ⌃⌥↓ minimized; if the next snap key is ⌃⌥↑ and it is still minimized, restore it. Any other focus change clears the memory.

Builds on: WindowLayout/SnapController.swift, SnapEngine.swift (pure, testable); the same rule as DockClick's minimized-by-click.

Risks: Low.

I02

Close a window from the ⌘Tab switcher

Value HighEffort S–MFits SCOPE

Windows: Delete closes the selected window in Alt+Tab; Windows 11 shows an × on the tile under the mouse.

In DockFlip: ⌘W closes the selected card (⌘ is held already; plain letters are the filter), the stack stays open and moves to the next card. An × on hover in the grid. Close only: quit, minimize and hide would be taste.

Builds on: Switcher/SwitcherPanel.swift, SwitcherInput, registry.close and CloseFollowUp, which already brings a save sheet forward.

Risks: The selection must stay steady when the list shrinks. DockDoor users asked for the same (issue 1288).

I03

Middle-click a row in the Dock list to close it

Value HighEffort SFits SCOPE

Windows: Middle-click a taskbar thumbnail closes that window: a core mouse habit.

In DockFlip: otherMouseDown on a list row or card closes it. No new tap: the event lands in DockFlip's own panel. A second step, middle-click a Dock icon for a new window (press the app's menu item whose key is ⌘N), only if that lookup proves reliable.

Builds on: WindowList/WindowListView.swift, WindowListPopup.close.

Risks: The Dock-icon half widens the click tap to another button, so SECURITY.md's table must change, and ⌘N is not "new window" in every app.

I04

Snap Assist that lets typing through and keeps going

Value HighEffort S–MFits SCOPE

Windows: In Windows, the first other key closes Snap Assist, and after a quarter it offers the next empty region until the screen is full.

In DockFlip: Take only arrows, Return and Esc; close on any other key and pass it on. After a pick into a quarter, offer the next empty region. This also makes the privacy sentence about ordinary keys true again.

Builds on: WindowLayout/SnapAssistPanel.swift (handleKey), SnapAssist.remainingRegion.

Risks: Low.

I05

⌃⌥1…9 again steps through that app's windows

Value HighEffort MFits SCOPE

Windows: Win+number repeated steps through the app's windows with the thumbnails shown; letting go of Win picks one.

In DockFlip: The first press works as now. A second press with ⌃⌥ still held opens the Dock list above that icon with the next window selected; each press steps; letting go of ⌃⌥ focuses it. Today the second press minimizes the window.

Builds on: Dock/DockController+Clicks.swift, DockAppOrder, WindowListPopup, and the listen-only modifier tap pattern from SwitcherKeyTaps.

Risks: The release tap needs the same care as ⌘Tab under secure input.

I06

Resize two snapped windows together

Value Medium–HighEffort M–LFits SCOPE

Windows: Dragging the shared edge of two snapped windows resizes both. This is what makes snapping feel finished.

In DockFlip: Remember pairs made by Snap Assist or by two snaps side by side. When one member's shared edge moves, set the neighbour's frame once on mouse-up. No divider handle, no overlay.

Builds on: The per-window snap record proposed in the snap-size finding, the registry's resized notifications, FrameSetter. A new pure SnapPairs type carries the tests.

Risks: Minimum sizes and terminals' size steps get in the way. Fix the snap-size finding first.

I07

Outline peek when hovering a row

Value MediumEffort S–MFits SCOPE

Windows: Aero Peek: hovering a taskbar thumbnail shows that window in place.

In DockFlip: Hovering a row draws an accent outline at that window's real frame on its display. It raises nothing and touches no pixels, so it works without Screen Recording: Aero Peek the DockFlip way.

Builds on: WindowLayout/SnapOverlay.swift, WindowListModel.setHovered, registry.knownFrame.

Risks: An outline of a fully covered window may confuse; perhaps only when part of it shows.

I08

The ⌘Tab filter also finds browser tabs

Value MediumEffort MFits SCOPE

Windows: Windows 11 can show Edge tabs in Alt+Tab; SCOPE.md already cites it.

In DockFlip: No tab cards. Once a filter is typed, a window also matches when one of its tabs contains the text; the card names the tab and Return goes straight to it.

Builds on: WindowList/BrowserTabs.swift, the SwitcherFilter rules, the existing pick-tab path.

Risks: Tab reads are slow: start them only when typing begins and never inside the 50 ms budget. Fix the failed-tab-read finding first.

Keyboard into the Dock list (⌃⌥T)

Value MediumEffort MFits SCOPE

Windows: Win+T focuses the taskbar; arrows move, Enter picks.

In DockFlip: ⌃⌥T opens the list of the front app above its icon as a key, non-activating panel. ↑↓ move, ←→ go to the next Dock app, Return picks, Esc cancels. It is also the missing VoiceOver route into the list.

Drag a file over a Dock icon to reach a window

Value Medium–HighEffort MFits SCOPE

Windows: Drag a file onto a taskbar button, wait, the window comes forward, drop into it.

In DockFlip: While a drag is on and the Dock highlights an app, open the list; resting on a row for half a second (one-shot wait) focuses that window. The drop itself is never taken.

Builds on: Dock/DockController.swift hover, WindowListPopup.

Risks: Unverified whether the Dock reports hover during a drag. Build a trial first.

Retake the shortcuts when the other app quits

In DockFlip: When AltTab or Rectangle quits, take ⌘Tab and the ⌃⌥ keys at once, replacing the manual Try Again. One didTerminateApplication observer, no timer.

"Not responding" and Force Quit where the user is looking

Considered and rejected

  • Clipboard history (Win+V). The most-named complaint outside window handling, but there is no pasteboard-changed event, so it needs a repeating timer, and it means reading everything copied.
  • Move a window to another desktop. Much wanted in Rectangle (issues 85 and 215, over 20 votes each), but only private Spaces calls do it, and they are locked down.
  • Real Aero Peek, always on top, Start menu, thirds and gaps, a tray, Dock progress bars, snap layouts, a Dock per display. On SCOPE's out-of-scope list or impossible without weakening system protection. The outline peek above is the honest version of the first.
  • Win+M, Win+Tab, Win+Ctrl+arrows, Win+Shift+S, Aero Shake. Covered by ⌃⌥D or by what macOS has itself (Mission Control, ⌃ arrows, ⌘⇧4, Hide Others).
  • Quit an app when its last window closes. Automatic and destructive (Mail, downloads, menu bar apps). Clean Up's suggest-only list is the right answer.
  • Close a browser tab from the list. Built in PR #4 and removed in PR #10: browsers do not expose the tab's close button reliably.
  • Customizable shortcuts, sort options, number keys for windows. Settings for taste; type-to-filter covers the need.
  • An update check. Networking, and explicitly banned.
  • Lock the screen with ⌃⌥L (Win+L). Tempting, but there is no public call for it: it would be a made-up key press or another private call.

Improvements that are not features

  • Notarization or a Homebrew tap. The first-launch warning is the largest hurdle a new user meets. SCOPE and ROADMAP already promise a tap that does not exist; building it would also give users an update channel without any networking code in the app.
  • Learning about updates without networking. With no update check, people on an old build never find out. A local one-time "What's new in x.y" line in the menu after a version change needs no network.
  • Reduce Motion and Reduce Transparency. No file in Sources reads these system settings. Flip 3D's spring and the frosted panels should follow them; it adds no setting.
  • Keyboard layouts. KeyCode.d, .e and the digits are fixed key codes, so on Dvorak ⌃⌥D sits on another printed key than the docs say. Resolve key codes from the current layout at registration, or say so in the docs.
  • Stage Manager. Test and then fix or document; see Needs investigation.
  • A real-Mac test table. Troubleshooting's "Tested on" table has only the CI runner. Add rows from debug-log self-checks on real macOS 26 machines, and let the launch check fail on a FAILED self-check line so a runner image that breaks a private call is caught before users meet it.
  • A menu item that removes DockFlip properly. People who drag the app to the Trash must follow the wiki by hand to remove the login item and turn edge tiling back on; NativeEdgeTiling and LoginItem already have the pieces.
  • A managed-settings profile for IT. A second .mobileconfig for the three managed keys beside the Accessibility profile, from make-pppc-profile.py.
